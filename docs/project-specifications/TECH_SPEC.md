# Technical Specification — European Trip Guide (v2)

This replaces the simple version described in PLAN.md sections 4-5. PLAN.md
still covers the agent framework/setup; this file covers what the product
actually is and how it's built.

## 1. Product summary

Two comprehensive, interactive city guides (Madrid, Paris), 15 places each.
Guides are a **paid product** (mock payment, no real money). Visitors get a
free preview of 3 places per city; the rest unlock after a (fake) purchase.
Logged-in users can bookmark favorite places and rate/comment on them.

## 2. Stack

| Layer | Choice |
|---|---|
| Backend | ASP.NET Core 10 (LTS) Web API |
| Frontend | React / Next.js |
| Database | SQLite, via EF Core — users, favorites, ratings, purchases only |
| Guide content | Static JSON files (`content/madrid.json`, `content/paris.json`), written by the Writer agent — **not** in the database |
| Auth | ASP.NET Core Identity, cookie-based sessions |
| Map | Leaflet + OpenStreetMap tiles (free, no API key needed) |
| Payments | None — purchase is simulated by writing a row to the database |

Why content stays as JSON and not in SQLite: it's regenerated by the Writer
agent, not user-submitted, so a database adds migration overhead for no real
benefit at this stage. User-generated data (accounts, favorites, ratings,
purchase records) goes in SQLite because it's relational and per-user.

## 3. Guide content schema (Writer agent output)

Each city guide (`content/{city}.json`):

```json
{
  "city": "Madrid",
  "intro": "short hook paragraph for the guide as a whole",
  "places": [
    {
      "slug": "museo-del-prado",
      "name": "Museo del Prado",
      "why_go": "1-2 sentence hook, used in previews/cards",
      "description": "longer paragraph — this is paid content, make it genuinely comprehensive, not a rehash of why_go",
      "how_to_get_there": "concrete transport directions",
      "cost": "approximate price, or 'check current price'",
      "booking_tip": "advance booking / best time / how to book",
      "lat": 40.4138,
      "lng": -3.6921,
      "is_preview": true
    }
  ]
}
```

Rules:
- Exactly 15 places per city.
- Exactly 3 of them have `"is_preview": true` — pick the 3 most enticing ones
  to hook a visitor into buying, not just the first 3 alphabetically.
- `slug` is a unique, kebab-case id per place (stable — used by favorites and
  ratings to reference a place without re-matching on name text).
- `lat`/`lng` are approximate coordinates for the map pin. The Writer agent
  should give its best-known coordinates for well-known landmarks; if
  genuinely unsure, use the neighborhood center rather than guessing wildly.
  This is a known accuracy limitation for v1 — a real geocoding tool would be
  a good v2 improvement.

## 4. Database schema (SQLite, EF Core, backend-owned)

- **Identity tables** (standard ASP.NET Core Identity: `AspNetUsers`, etc.) —
  email + password hash, created automatically by `AddIdentity<...>()`.
- **Purchases**: `Id, UserId (FK), City, PurchasedAt`
- **Favorites**: `Id, UserId (FK), City, PlaceSlug, CreatedAt`
- **Ratings**: `Id, UserId (FK), City, PlaceSlug, Stars (1-5), Comment, CreatedAt`
  — one rating per (UserId, City, PlaceSlug), upsert on repeat POST.

Guide price is a backend-side constant for v1 (e.g. $4.99 per city) — not
something the Writer agent decides.

## 5. API (ASP.NET Core Web API)

**Auth**
- `POST /api/auth/register` `{ email, password }`
- `POST /api/auth/login` `{ email, password }` → sets auth cookie
- `POST /api/auth/logout`
- `GET /api/auth/me` → current user or 401

**Guides**
- `GET /api/guides` → `[{ city, intro, price, purchased }]` (`purchased` is
  `false` for anonymous users)
- `GET /api/guides/{city}` →
  - Preview places (`is_preview: true`): full data (incl. lat/lng)
  - Non-preview places, if the current user hasn't purchased: `{ slug, name, why_go, locked: true }` only — no description/cost/booking_tip/coordinates
  - Non-preview places, if purchased: full data
- `POST /api/guides/{city}/purchase` (auth required) → creates a Purchase row, mock only

**Favorites** (auth required)
- `GET /api/favorites`
- `POST /api/favorites` `{ city, placeSlug }`
- `DELETE /api/favorites/{id}`

**Ratings**
- `GET /api/guides/{city}/places/{slug}/ratings` → list + average (public)
- `POST /api/guides/{city}/places/{slug}/ratings` `{ stars, comment }` (auth required, upsert)

CORS must allow the Next.js dev origin (`http://localhost:3000`) with
credentials enabled (cookies need `credentials: "include"` on the frontend
and a matching CORS policy on the backend).

## 6. Frontend pages (React / Next.js)

- `/` — home: both guides as cards (intro, price, purchased/not, "Buy" or "Open")
- `/login`, `/register` — auth forms
- `/guides/[city]` — the interactive guide:
  - Map (Leaflet) with a pin per **visible** place (preview places always,
    the rest once purchased)
  - Place cards in order: preview places shown in full; locked places shown
    as a teaser card (name + why_go + a lock icon) with a "Buy to unlock" CTA
  - Prominent purchase button/banner if not yet purchased
  - Favorite (bookmark) toggle and a rating/comment widget on each unlocked place
- `/favorites` — the current user's saved places across both cities
- Nav bar reflecting logged-in/out state

## 7. Ground rules specific to this version

- Purchases are simulated. Never wire up a real payment processor or ask for
  real card details.
- One rating per user per place — posting again updates the existing rating,
  it doesn't create a duplicate.
- Locked place data must never be sent to the frontend for non-purchasers
  (no description/cost/coordinates in the API response) — this is a real
  security/product requirement, not just a UI hide.

## 8. Design direction

Style reference: [Behance – Travel & Tourism Website UI/UX Design](https://www.behance.net/gallery/252212709/Travel-Tourism-Website-UIUX-Design)
(a Bali retreat booking concept). This is inspiration only — described in
words below, not copied assets. It's someone else's portfolio work, so don't
reuse its actual images or exact layouts verbatim; build an original
implementation of the same *feel*.

**Overall feel:** editorial, photo-led travel branding — closer to a
boutique magazine than a generic listings site.

- **Photography carries the color.** Full-bleed, high-quality landscape
  photos of the actual places do most of the visual work. UI chrome (nav,
  buttons, text) stays neutral — white, black, gray — so photos stay the
  focal point.
- **Typography pairing:** an elegant serif italic for display headlines/
  emphasis words (e.g. a hero line like "*Where the City Meets You*"),
  paired with a clean, light sans-serif for body text and nav. Free Google
  Fonts that give this look: **Playfair Display** or **Cormorant** (serif,
  use italic weight) + **Inter** or **Manrope** (sans).
- **Buttons:** pill-shaped (fully rounded), not sharp-cornered — e.g. a
  white "Buy this guide" pill over a photo, dark pill nav items.
- **Info chips:** small rounded badges with an icon + short label for quick
  facts — for us: "Free preview", "Metro nearby", "~€12", "Book ahead".
- **Cards:** rounded corners (12-16px), photo-dominant, place name + one-line
  hook overlaid at the bottom in white text over a subtle dark gradient —
  this works well for the 15-place grid on each guide page.
- **Hero sections:** a semi-transparent dark nav bar floating over the photo
  rather than a solid color bar.
- **Rhythm:** alternate photo-heavy full-bleed sections (hero, place detail)
  with airy white sections that have generous whitespace (the guide list,
  typography-only statement sections).
- **Optional itinerary/timeline pattern:** numbered steps with a thin
  vertical line, day-by-day — could work well if you ever want a "walk it in
  order" view of the 15 places, worth keeping in mind but not required for
  v1.

**Photos:** use real, royalty-free photos of the actual Madrid/Paris places —
[unsplash.com](https://unsplash.com) or [pexels.com](https://pexels.com),
both free with no attribution required, search each place by name.

## 9. Testing expectations

- Backend: xUnit tests, at minimum covering register/login, the preview vs
  locked response shape for `/api/guides/{city}` (anonymous vs purchased),
  and the favorites/ratings endpoints.
- Frontend: `npm run build` must succeed; spot-check that a locked place
  never renders its description/cost even if present in dev data.
